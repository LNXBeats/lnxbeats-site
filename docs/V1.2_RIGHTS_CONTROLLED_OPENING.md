# V1.2 — Ouverture contrôlée Rights 150 €

Statut de ce document : préparation opérateur. Le commerce Rights reste fermé et aucune mutation Production n'est décrite comme déjà effectuée.

## États d'ouverture

Les nouvelles ventes dépendent d'un état unique calculé par `evaluateRightsCommerce` :

| État | Sens | Nouvelles demandes / checkout |
| --- | --- | --- |
| `BLOCKED` | préconditions techniques ou contractuelles incomplètes, ou configuration partielle | refusés côté serveur |
| `READY_NOT_OPEN` | offre et code prêts, aucune ouverture demandée | refusés côté serveur |
| `OPEN` | contrat v3 exact approuvé et configuration complète | possibles pour une commande encore éligible |

La configuration absente reste fermée. En Production, l'ouverture exige simultanément `RIGHTS_COMMERCE_ENABLED=true`, `RIGHTS_PAYMENTS_ENABLED=true` et `RIGHTS_PRODUCTION_CONFIRM=enable-production-rights-commerce`. Une valeur partielle produit `BLOCKED` avec une raison Admin exploitable. Les flags Shop ou la seule présence de credentials Stripe/PayPal n'ouvrent jamais Rights.

La fermeture des nouvelles ventes n'interrompt pas les dossiers déjà engagés : capture PayPal déjà autorisée, preuves provider, réconciliation locale, rétractation, remboursement approuvé et activation différée conservent leurs propres guards. Aucun de ces parcours ne crée une nouvelle vente par inférence.

## Contrat v3

Le dossier exact soumis à revue est [V1.2_RIGHTS_V3_APPROVAL_PACKAGE.md](V1.2_RIGHTS_V3_APPROVAL_PACKAGE.md). Il contient le texte canonique intégral, l'identifiant Production observé, les deux empreintes documentées et le commit d'origine. L'ouverture lie l'offre `PUBLICATION_LICENSE` à la version 3 et à son empreinte canonique ; une autre version ou un texte différent est refusé.

L'approbation normale reste l'action Admin authentifiée sur `/admin/droits`. Elle exige une référence de revue juridique réelle et enregistre l'Admin, la date réelle, la version et l'empreinte. L'approbation seule n'ouvre pas le commerce. Au présent checkpoint, le modèle Production reste `DRAFT`.

## Matrice PostgreSQL minimale

Les rôles runtime observés sont NOSUPERUSER/NOCREATEDB/NOCREATEROLE. Les permissions sont limitées aux opérations métier nécessaires :

| Service | Ressources | Opérations requises |
| --- | --- | --- |
| Web | Rights requests/events/licenses/withdrawals, Payments/provider events/refunds, contrats/acceptations/templates, facturation et outbox associée | `SELECT`, puis `INSERT`/`UPDATE` uniquement selon le parcours ; usages des séquences Rights/documentaires déjà attribués |
| Notifications | outbox, événements de notification, suppressions et sources minimales | `SELECT`, claim par `UPDATE`, audit par `INSERT` |
| Maintenance | licences, demandes, documents | `SELECT`, `UPDATE` |
| Maintenance | rétractations, modèles et acceptations | `SELECT` |
| Maintenance | événements Rights | `SELECT`, `INSERT` |

La lecture Production a trouvé le Web et Notifications complets. Elle a identifié uniquement les droits Maintenance listés dans `scripts/sql/rights-maintenance-runtime-grants.sql`; ce patch n'accorde ni `ALL`, ni ownership, ni `DELETE`/`TRUNCATE`. Il doit être exécuté ultérieurement par le rôle de migration contrôlé, jamais par un runtime.

La preuve locale ouvre de vraies connexions PostgreSQL sous trois rôles distincts NOSUPERUSER : activation légitime une fois, rejeu sans effet, notification unique, aucun événement provider/refund ajouté, DDL et suppressions destructives refusés.
