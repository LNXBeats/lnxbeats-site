# V1.2 — Admin Operations et préparation Droits & contrats

Ce document décrit le cockpit opérationnel, le nettoyage sécurisé et le gate du commerce Droits préparés pour V1.2. Il ne constitue ni une autorisation de modifier Production, ni une validation juridique des modèles contractuels.

## Définition de « À traiter »

Le fait d’ouvrir un dossier ne modifie aucun voyant. Une action provient uniquement d’un état persistant : étape de création à réaliser, paiement ou incident en revue, remboursement dû ou ambigu, ShopOrder payée à préparer/expédier, demande client ouverte, revue logistique, dossier Droits à une étape Admin, notification en échec ou lease interrompue, ou SAV non finalisé.

Une ShopOrder annulée et remboursée sans autre revue est terminée. Une attente de paiement reste dans « En attente client » et n’est pas comptée comme intervention Admin. Les priorités critiques utilisent un libellé en plus de la couleur. Une archive qui acquiert ultérieurement une action doit réapparaître dans les vues opérationnelles.

## Nettoyage : supprimer, archiver ou conserver

La prévisualisation classe chaque cible côté serveur, puis le serveur recalcule cette classification sous transaction juste avant l’opération :

- `DELETE_SAFE` : uniquement une commande musicale `DRAFT` ou `CANCELLED`, explicitement identifiée comme fixture par un domaine non délivrable réservé, sans paiement, fichier, facture, avoir, remboursement, notification, droit, rétractation, livraison ni historique protégé ;
- `ARCHIVE_REQUIRED` : dossier terminé dont les pièces ou l’historique doivent rester intacts ; l’overlay d’archive ne change jamais son statut métier, son stock ou ses documents ;
- `KEEP_ACTION_REQUIRED` : dossier actif, attente client, revue financière/logistique, notification défaillante, rétractation ou relation contractuelle encore ouverte.

Les noms « QA » ou « test » ne suffisent jamais. Une ShopOrder et une demande de droits ne sont jamais hard-deleted par cet outil. Les clés financières, documents, événements provider et audits restent hors du chemin de suppression.

Le plan affiche avant validation les comptes exacts de suppressions, archives et éléments ignorés. La confirmation est explicite, same-origin et Admin. Un verrou PostgreSQL sérialise deux nettoyages ; les contraintes relationnelles et le recalcul font échouer le plan si une preuve de conservation apparaît entre prévisualisation et confirmation. Chaque opération réussie écrit un audit minimal. Une relance d’archive est idempotente.

Une fixture portant encore un fichier n’est jamais hard-deleted : elle doit être archivée ou examinée. Ce choix fail-closed évite de perdre la clé d’un objet privé en l’absence de file durable de purge et de réconciliation.

### Procédure Production future

1. Exécuter l’inventaire READ-ONLY et conserver la sortie sans PII.
2. Faire valider humainement chaque référence proposée, en particulier les dossiers `KEEP_ACTION_REQUIRED`.
3. Déployer d’abord la migration additive et le code, sans exécuter de nettoyage automatique.
4. Ouvrir `/admin/nettoyage`, comparer la classification courante à l’inventaire approuvé et sélectionner seulement les références autorisées.
5. Relire le résumé exact, confirmer une fois, puis contrôler Archives, compteurs, audits et éventuels objets privés à réconcilier.

Aucune opération en masse ne doit être lancée depuis SQL ou à partir d’un motif de titre.

## Droits & contrats : offres et gates

Les prix serveur restent centralisés dans `data/rights-offer.ts` :

- licence de publication via distributeur : `15_000` centimes, version `2026-08-rights-v2` ;
- partenariat d’exploitation lié au volet SACEM : `150_000` centimes, version `2026-08-rights-v2`.

Les 1 500 € sont le prix d’une offre LNX Beats, pas un tarif SACEM, une garantie d’admission, de déclaration, de répartition ou de revenu. Le détail contractuel n’est pas complété par inférence.

Le gate est fail-closed avec trois états : `BLOCKED`, `READY_NOT_OPEN`, `OPEN`. V1.2 conserve l’ouverture explicitement impossible : les modèles attendent une revue juridique réelle, leur `sourceMarkup` approuvé n’est pas encore lié au renderer, les documents sont préparatoires, aucun `Payment`/`Invoice` n’est rattaché à `RightsRequest` et les invariants PostgreSQL interdisent toujours `ACTIVE`. Aucune offre publique payable n’est ajoutée.

Avant toute ouverture future, une décision humaine doit fixer la portée, durée, territoire, exclusivité, obligations, résiliation, conditions de paiement et documents de chaque offre. L’implémentation devra ensuite figer la version contractuelle réellement rendue, rattacher le paiement serveur au dossier, facturer, auditer et activer de manière idempotente avec isolation LIVE/TEST. Le module Droits ne doit jamais bloquer Commander, Shop, Notifications ou Maintenance.

Le dossier complet, les tableaux `FOUND` / `MISSING` / `CONFLICTING`, les libellés publics candidats et les huit décisions structurantes sont consignés dans [V1.2_RIGHTS_CONTRACT_DECISION_PACK.md](V1.2_RIGHTS_CONTRACT_DECISION_PACK.md).

## Migration, déploiement et rollback

La migration `20260908120000_admin_operations_archives` est additive : elle crée l’overlay d’archive et le journal de nettoyage, sans réécrire de donnée existante. Le déploiement futur doit appliquer les migrations avec la procédure habituelle, vérifier les 30 migrations, puis contrôler `/admin`, les filtres, la navigation mobile, le registre de facturation, le catalogue paginé et le gate Droits.

Rollback applicatif : revenir au déploiement Web stable précédemment validé. La migration additive peut rester en place ; supprimer ses tables ou types en Production n’est pas un rollback sûr. Les archives créées après une éventuelle autorisation Production doivent être conservées et examinées avant tout retour applicatif. Aucun rollback ne doit modifier un paiement, une pièce comptable, un stock ou un statut métier.

## Audit et commandes de validation

- inventaire Production : `npm run admin:inventory:production`, uniquement dans Railway Production avec la confirmation dédiée ; le script ouvre explicitement une transaction READ ONLY et n’émet que des champs allowlistés ;
- runtime PostgreSQL jetable : `npm run test:admin-operations:runtime` avec les guards locaux et la preuve d’instance Prisma Dev ;
- tests : Admin, Orders/Shop, Droits, Billing presentation, Auth/Security et suite canonique ;
- quality gates : Prisma format/validate/generate, lint, typecheck, build, audits npm, dépendances, secrets, bundle client et `git diff --check`.

Ni l’inventaire ni les tests n’appellent Stripe, PayPal, Resend ou une base Production depuis le runtime local.
